# Provenance Ledger

When a team ships code that was generated by an AI agent, a question arises that traditional development never had to answer: _who_ produced this artefact? Not which developer committed it, but which agent, running which model, with which prompt, at which iteration, produced the text that became this code.

For internal tooling, this question is academic. For regulated industries, banking, healthcare, legal, it's a compliance requirement. Auditors want to trace a deployed artefact back through the chain of decisions that produced it. Git history tells you _what_ changed and _when_. It doesn't tell you which AI system was involved, what context it was given, or how many attempts it took to produce an acceptable result.

[Session Checkpoint](session-checkpoint.md) preserves full session transcripts for replay and rollback. The Provenance Ledger solves a different problem: lightweight, structured traceability from any artefact to the AI system that generated it.

## How It Works

The approach maintains a structured log, typically a LEDGER.md file within the feature's working directory, that records a provenance entry for every AI generation step. Each entry captures the agent name, the model and version used, a timestamp, the task or phase that triggered the generation, the outcome (pass, fail, iterate), and the iteration count.

The ledger is append-only and committed to Git alongside the artefacts it describes. This means the provenance record is versioned, immutable once committed, and co-located with the code it traces.

### What Gets Recorded

A typical entry looks like this: the spec-writer agent, running claude-opus-4-6, produced SPEC.md for task REQ-042 on its second iteration after the critic requested changes on the first pass. The entry records enough to answer "what produced this?" without recording the full transcript (that's what Session Checkpoint is for).

### Paired with Git

The ledger and Git together provide complete traceability. Git records what changed, when, and on which branch. The ledger records which AI system produced the change, under what constraints, and how many attempts it took. A sign-off record links a specific ledger entry and Git SHA to a human approval decision.

For compliance reviews, this chain is valuable: deployed artefact → Git SHA → ledger entry → agent, model, and iteration → human sign-off. Every link is in the repository.

### Lightweight by Design

The ledger is deliberately minimal. It records structured metadata, not transcripts. This keeps it small enough to review at a glance and cheap enough to maintain on every generation step. Teams that need full transcripts use [Session Checkpoint](session-checkpoint.md) alongside the ledger, not instead of it.

## The Trade-offs

The benefits centre on auditability. You can trace any artefact to the AI system that produced it. Compliance reviews have a clear evidence chain. Model version changes are visible in the record, so you can correlate quality changes with model upgrades. And the overhead is minimal: one structured entry per generation step.

The costs are modest. The agent must write a ledger entry on every generation step, which is a small but non-zero overhead. The ledger format must be defined and maintained as a convention. And the ledger alone doesn't explain _why_ the agent made a particular decision; for that you need Session Checkpoint or the agent's own reasoning in the artefact.

## When to Use It

This pattern is valuable for regulated industries where AI-generated artefact provenance must be demonstrable, teams using multiple models or model versions who want to correlate output quality with model changes, organisations building trust in AI-assisted development who need to show the chain from deployment to reasoning, and any environment where "which AI produced this?" is a question someone will ask.

It's unnecessary for personal projects and prototypes where traceability adds no value, teams using a single model version in a stable environment, and situations where Git history alone provides sufficient audit trail.

This complements [Session Checkpoint](session-checkpoint.md), which provides full session replay, while the ledger provides lightweight structured provenance. It supports [Post-Inference Validation](post-inference-validation.md) by providing the provenance metadata that validation decisions can reference. And it integrates naturally with [Specify Plan Ship](specify-plan-ship.md), recording provenance at each phase transition.
